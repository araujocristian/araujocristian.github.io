### TL;DR

A aula apresenta a taxonomia canônica de três níveis de adoção de SDD — **Spec First**, **Spec Anchored** e **Spec as Source** — em sintonia direta com o artigo de referência de Birgitta Böckeler (Thoughtworks/Fowler, out/2025). O professor sinaliza que o curso vai operar predominantemente no nível intermediário (Spec Anchored) e reconhece, com pé no chão, que Spec-as-Source pleno ainda é mais aspiração que realidade fora de domínios maduros como geração de stubs OpenAPI ou código embarcado certificado.

### Resumo Expandido

A aula 2 entrega o que a aula 1 prometeu: a teoria substantiva do SDD começa aqui, com a definição operacional ("a especificação é a fonte da verdade para o código gerado") e a **escala de maturidade** que estrutura a discussão do campo em 2026. O professor é fiel à literatura — os três níveis que ele apresenta vêm diretamente do artigo _Understanding Spec-Driven-Development: Kiro, spec-kit, and Tessl_ de [Birgitta Böckeler](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html), publicado no blog do Martin Fowler em 15/10/2025. Isso é importante: você está aprendendo o vocabulário compartilhado da indústria, não uma versão particular.

O **primeiro nível, Spec First**, é o que mais se aproxima da prática que vocês já viram com Luiz Carlos no curso anterior (planejar → implementar). A diferença, como o professor bem nota, é o **grau de formalidade da spec** e o quanto a geração dela é **automatizada** — você usa IA para gerar uma spec densa, executa a feature, e descarta. É o modelo de "use uma vez, jogue fora". Funciona para protótipos, scripts, fixes pontuais e features isoladas em sistemas que não exigem rastreabilidade.

O **segundo nível, Spec Anchored**, é o coração operacional do que se faz em produção em 2026 e onde o curso vai morar. Aqui a spec **vive junto ao código**, evolui com ele e serve como referência permanente — não para regenerar tudo, mas para responder "por que essa parte do sistema é assim?" e para dar contexto a IAs em sessões futuras. O professor levanta uma dor real e honesta: **manter spec sem ambiguidade ao longo do tempo é quase impossível**. Documentos divergem do código, decisões mudam, contradições aparecem. Esse problema tem mitigação parcial via **contratos-em-código** (vimos na aula 1) e via **gates de validação** (que serão tema do harness mais à frente), mas não há solução final.

O **terceiro nível, Spec as Source**, é o radical: a spec é o único artefato editável; o código carrega o famigerado comentário `// GENERATED FROM SPEC - DO NOT EDIT`. O professor, com razão, pondera que isso "depende muito do nível de interpretação". A literatura concorda — Böckeler observa que apenas Tessl, entre as três ferramentas que ela analisou, **aspira** a esse nível, e mesmo assim ainda em beta com mapeamento 1:1 spec→arquivo. Onde Spec-as-Source já é prática consolidada há anos é em **domínios estreitos com geradores maduros**: stubs de servidor a partir de OpenAPI, código C certificado a partir de modelos Simulink na indústria automotiva. Para software geral, ainda é fronteira.

A confissão do professor — _"hoje eu já não programo mais"_ — é tecnicamente um movimento na direção de Spec-as-Source vivido na prática individual. Ele continua "ajustando variável de ambiente, fazendo um negócio aqui e ali", mas a codificação principal saiu da mão. Esse é o vetor em que toda a indústria está se movendo: o engenheiro sai do papel de produtor de código e vira designer de spec + curador de output. Esse deslocamento é o que a OpenAI articulou em 2026: _"what changes when a software engineering team's primary job is no longer to write code, but to design environments, specify intent, and build feedback loops"_.

### Deep Dive: Conceitos & Teoria

**Spec First (Nível 1)**

- 🎓 _Na aula:_ "A especificação é criada antes do código, mas não necessariamente é mantida. Utilizada para protótipos e tarefas isoladas."
- 🔍 _Deep Dive:_ Forma mais leve de SDD. A spec serve como **artefato de transição** — input para o agente, descartável após geração. Böckeler ilustra com diagrama: spec → código, depois spec é deletada; em manutenção futura, nova spec é criada para descrever a mudança e depois descartada de novo. Vantagem: zero overhead de manutenção, ganho imediato em desambiguação. Desvantagem: o "porquê" das decisões evapora junto com a spec; em sistemas que evoluem, isso vira dívida cognitiva. É o modo que melhor serve **greenfield isolado** e **fixes complexos pontuais**. Em termos do tier declaration que vimos na aula 1, encaixa em `MEDIUM` ocasional.

**Spec Anchored (Nível 2) — onde o curso vai operar**

- 🎓 _Na aula:_ "A especificação é mantida junto com o código, validada com os testes, vive junto e evolui com o sistema."
- 🔍 _Deep Dive:_ A spec se torna **artefato de primeira classe no repositório**, versionada com o código, revisada em PR, e usada em duas direções: (a) para humanos e agentes entenderem por que algo é como é, (b) para validação contra implementação (testes amarrados a acceptance criteria). Böckeler descreve como spec é editada _junto_ com o código durante manutenção — não deletada como em Spec First, não a única fonte como em Spec as Source. **A grande dor** que o professor menciona — manter sem ambiguidade — é exatamente o que Alberto Souza (Nubank) documentou em ~70 specs de produção: prosa diverge silenciosamente, contratos não. Por isso a recomendação canônica de 2026 é **prosa para "porquê", contrato para "o quê"**. Em harnesses como Claude Code e Cursor, esse nível é implementado via memory files (`AGENTS.md`/`CLAUDE.md`/`.cursorrules`) + skills com directive descriptions + `feature_list.json` rastreando dependências. Spec Anchored é o _sweet spot_ de custo/benefício para times de 2–20 pessoas em produção.

**Spec as Source (Nível 3) — a fronteira aspiracional**

- 🎓 _Na aula:_ "A especificação é o único local onde você edita. O código gerado nunca é modificado na mão. Vamos chegar lá, mas não tão ao pé da letra."
- 🔍 _Deep Dive:_ O código tem comentário literal `// GENERATED FROM SPEC - DO NOT EDIT` no topo. A única forma de evoluir o sistema é **editar a spec e regenerar**. Böckeler nota que [Tessl](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html) é o único dos três frameworks (Kiro, spec-kit, Tessl) que aspira a esse nível, e ainda em beta com mapeamento 1:1 (uma spec → um arquivo). O paralelo histórico mais útil é com **MDD (Model-Driven Development)** dos anos 2000 — Simulink/IBM Rational — que conseguiu Spec-as-Source em domínios estreitos (controle embarcado, sistemas críticos) mas falhou em código de aplicação. A questão aberta de 2026 é se LLMs mudam essa equação ao tornar a geração robusta o suficiente para domínios mais amplos. O paper _Spec-Driven Development: From Code to Contract in the Age of AI Coding Assistants_ (arXiv 2602.00180, fev/2026) argumenta que sim em médio prazo; Fowler é mais cético. **A previsão honesta:** Spec-as-Source pleno em software de aplicação ainda é evento futuro; o que existe hoje é **deslocamento gradual** — engenheiros como o professor que "já não codificam" mas ainda intervêm em pontos cirúrgicos.

**Drift de documentação (a dor central)**

- 🎓 _Na aula:_ "Manter essas documentações extremamente sem ambiguidades é algo que, na minha opinião, é quase que impossível."
- 🔍 _Deep Dive:_ Diagnóstico correto. Em sistemas com 6+ meses de vida, prosa especificativa diverge do código com taxa observada de ~40% das afirmações por trimestre (Doernenburg, _Assessing internal quality while coding with an agent_, Thoughtworks 27/01/2026). Três contramedidas estabelecidas em 2026: (1) **contratos-em-código** como fonte da verdade para invariantes (TypeScript signatures, JSON Schema, OpenAPI) — prosa só para "porquê"; (2) **gates mecânicos** que rejeitam PR se o código diverge do contrato declarado; (3) **regeneração frequente da spec a partir do código** via tools como `tessl document --code` (engenharia reversa) — útil para auditar drift, não para substituir spec autoral.

### Engenharia: Arquiteturas e Padrões

**Mapeamento nível ↔ ferramenta ↔ harness**

```
                 Spec First           Spec Anchored          Spec as Source
                 ───────────          ─────────────          ──────────────
Spec lifecycle:  cria → usa →         cria → mantém →        cria → fonte única
                 descarta             evolui com código      → regenera código

Ferramenta       GitHub Spec Kit      AGENTS.md/CLAUDE.md    Tessl (beta)
canônica:        (modo simples)       + Spec Kit ciclo       OpenAPI codegen
                                      completo               Simulink

Onde mora        markdown na          repo: docs/specs/      repo: specs/*.tessl
a spec:          PR → deletada        + linked em código     + código gerado em /gen

Como SWE         "uma vez por         "vive no PR review"    "PR é só na spec;
interage:        feature, descarta"                          código diff é review"

Suporte de       baixo (não precisa)  médio (memory files +  alto (gen tool +
harness:                              skills + gates)        DO-NOT-EDIT enforcement)
```

**Spec Kit no modo Spec Anchored** — o que muda na prática

No nível 1 (Spec First), você roda `specify init` por feature, descarta a pasta `.specify/` ou move artefatos para um arquivo descartado. No nível 2 (Spec Anchored), o fluxo muda:

```bash
# Branch nova por feature (Spec Kit detecta pelo nome do branch)
git checkout -b 003-payment-refunds

# Constitution só uma vez por projeto, raramente atualiza
specify constitution

# Por feature: spec → plan → tasks ficam VERSIONADOS no repo
specify specify  # gera spec/003-payment-refunds/spec.md
specify plan     # gera spec/003-payment-refunds/plan.md
specify tasks    # gera spec/003-payment-refunds/tasks.md
specify implement

# Em manutenção: spec evolui junto com o código
# PR de bugfix toca código E spec.md, revisor avalia consistência
```

A diferença prática: no Spec Anchored, o reviewer aprende a perguntar _"a spec foi atualizada?"_ em todo PR não-trivial. Sem essa disciplina, o nível degrada para Spec First na prática (spec existe mas mente).

**Tessl como vislumbre de Spec-as-Source**

```bash
# Fluxo típico (beta, 2025-2026)
tessl init
# Você escreve manualmente a spec em formato Tessl
vim specs/freight-calculator.tessl
# Exemplo: contém @generate, @test, definição de API e invariantes

tessl build
# Gera src/freight-calculator.js com header:
# // GENERATED FROM SPEC - DO NOT EDIT
```

Limitações atuais relevantes para o aluno: 1:1 spec/arquivo, suporte JS (TS em roadmap), curva de aprendizado da DSL. O CLI duplica como **MCP server**, o que permite agente conversar com Tessl sem CLI manual.

### Pontos de Atenção e Trade-offs

- **Spec First que finge ser Spec Anchored.** O modo de falha mais comum em times que adotam SDD: cria-se spec na PR original, mas em manutenção ninguém atualiza. Em 6 meses, a spec mente ativamente. Mitigação: gate de PR que falha se código mudou e spec não.
- **Spec Anchored exige cultura de revisão de spec.** PRs revisam código por hábito; revisar spec é músculo novo. Sem disciplina explícita, o nível 2 vira nível 1 _de facto_.
- **Spec-as-Source só paga em domínio estável.** OpenAPI funciona porque a especificação de uma API REST é estreita e bem definida. Tentar Spec-as-Source em UI de produto, onde requisitos mudam toda sprint, gera retrabalho infinito da spec.
- **"Não programo mais" tem armadilha.** O professor é honesto sobre seu workflow, mas isso pressupõe domínio prévio profundo do código. Para um júnior, pular a fase de "colocar a mão" significa nunca desenvolver intuição para entender o que o agente está produzindo. Curva: codifique para aprender, especifique para escalar.
- **Granularidade da spec ajusta-se ao modelo.** O professor menciona que modelos melhores precisam de menos granularidade. Verdadeiro, mas com asterisco: a granularidade certa depende do **custo da falha**, não só da capacidade do modelo. Sistemas críticos (pagamento, healthcare) demandam contratos formais mesmo com Opus 4.7+.
- **Drift é inevitável; a pergunta é a taxa.** Aceite que prosa vai divergir. Coloque o esforço em (a) reduzir a quantidade de prosa via contratos-em-código, (b) detectar drift cedo via gates, (c) re-gerar spec a partir do código periodicamente para auditoria.
- **Migração entre níveis é unidirecional.** Subir de Spec First para Anchored é viável incremental; descer (abandonar specs maduras) destrói rastreabilidade e raramente se recupera.

### Nota do Pesquisador

> **Observação:** A apresentação do professor está alinhada ao artigo de referência de Birgitta Böckeler — a taxonomia, os exemplos e até o ceticismo sobre Spec-as-Source são consistentes. Dois pequenos pontos para enriquecer:
> 
> (1) O professor menciona "blog do Martin Fowler" sem creditar a autora. O artigo é assinado por **Birgitta Böckeler** (engenheira sênior da Thoughtworks), publicado no blog do Fowler como parte da série _Exploring Gen AI_. Vale citar corretamente em trabalhos acadêmicos.
> 
> (2) Spec-as-Source não é só aspiração futura — ela já existe há ~15 anos em domínios estreitos: **OpenAPI codegen** (servidores REST gerados a partir de YAML), **Simulink coder** (código C certificado para automotivo/aeroespacial), **Protocol Buffers** (DTOs gerados de `.proto`). Esses são casos vivos de spec-as-source que precederam a era IA. A novidade que LLMs trazem é a possibilidade de estender o paradigma para **domínios menos estruturados** — é exatamente isso que Tessl tenta. O paper [arXiv 2602.00180](https://arxiv.org/html/2602.00180v1) discute o paralelo em detalhe.

### Quiz Prático

**Perguntas sobre a aula:**

1. Qual é a diferença prática entre **Spec First** e **Spec Anchored** no momento em que uma feature é entregue e mergeada na main?
2. O professor afirma que manter especificações sem ambiguidade ao longo do tempo é "quase impossível". Quais três mecanismos a indústria usa em 2026 para mitigar essa dor sem eliminá-la?
3. O professor diz que "hoje já não programa mais" mas ainda faz "ajustes pontuais". Em qual dos três níveis de SDD esse fluxo se encaixa, e por que ele não é Spec-as-Source pleno?

**🚀 Desafio (conteúdo extra pesquisado):**

4. Spec-as-Source não é invenção da era IA. Cite dois domínios onde ele já é prática estabelecida há mais de uma década e explique por que esses domínios funcionam onde software de aplicação ainda fracassa.

---

**Respostas:**

1. **Em Spec First, a spec é descartada (ou arquivada como histórico morto) após o merge — o repositório fica só com o código.** Em Spec Anchored, a spec é versionada no repo (tipicamente em `docs/specs/` ou `spec/<feature>/`) e participa de toda futura revisão de PR daquela área do sistema. A diferença não está no momento de geração, mas no ciclo de vida pós-merge.
    
2. **(a) Contratos-em-código como fonte da verdade para invariantes** (TypeScript signatures, JSON Schema, OpenAPI), reservando prosa apenas para "porquê"; **(b) gates mecânicos** que falham PR se código diverge do contrato declarado ou se código mudou e spec correspondente não foi tocada; **(c) regeneração reversa periódica da spec a partir do código** (tools como `tessl document --code`) para auditoria de drift. Drift continua acontecendo, mas é detectado cedo em vez de descoberto em produção 6 meses depois.
    
3. **Spec Anchored, não Spec-as-Source.** Em Spec-as-Source pleno, o engenheiro só edita a spec e o código tem `// DO NOT EDIT`. O professor descreve um fluxo onde a spec/conversa com IA é o ponto principal de produção de código, mas ele ainda intervém diretamente no código gerado em ajustes pontuais (variáveis de ambiente, configurações, pequenos negócios). Essa intervenção manual no código gerado quebra o invariante de Spec-as-Source. É _quase_ Spec-as-Source, mas operacionalmente é Spec Anchored agressivo.
    
4. **OpenAPI/Swagger codegen** (gera stubs de servidor REST a partir de spec YAML; o `.yaml` é editado, código `_pb2.py` ou `*ServerStub.java` é regenerado) e **Simulink Coder** (modelos visuais de controle geram código C certificado para automotivo, aeroespacial e dispositivos médicos — DO-178C e ISO 26262). **Por que funcionam:** o domínio é estreito e formalmente definido (verbos HTTP + tipos JSON em REST; equações diferenciais + máquinas de estado em controle), o gerador é maduro e auditável, e o output tem critério objetivo de correção (conformidade de protocolo, certificação regulatória). **Por que software de aplicação fracassa:** o domínio é aberto (UX, regras de negócio mutáveis, integrações heterogêneas), o gerador (LLM) é estocástico, e "correto" é ambíguo. LLMs podem fechar parte dessa lacuna em domínios intermediários — é a aposta de Tessl — mas não em UI de produto evoluindo a cada sprint.

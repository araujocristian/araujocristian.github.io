### TL;DR

Aula de abertura: o professor posiciona o **Spec-Driven Development (SDD)** como o próximo degrau após dominar planejamento, skills e MCP, e antecipa uma decisão didática deliberada — começar com SDD "puro", **sem harness ao redor**, para isolar os conceitos. Ele também avisa que SDD é amplo e prefere skills próprias em vez de adotar um framework canônico. A aula em si é leve em conteúdo técnico, mas marca uma transição importante: você está saindo de "como prompt + tool funciona" para "como spec governa código gerado por agentes".

### Resumo Expandido

O professor abre o capítulo de SDD após assumir que três bases já estão consolidadas no aluno: **planejamento de tarefas**, **implementação assistida**, uso de **skills** e integração via **MCP (Model Context Protocol)**. Essa é a fronteira entre as eras III (context engineering) e IV (harness + SDD) da disciplina, e ele faz a passagem explícita: agora o foco se desloca de "compor o que o modelo vê" para "especificar o que o modelo deve construir, antes de construir".

A escolha pedagógica mais importante da aula é a separação artificial entre **SDD** e **harness/boundaries**. Na prática de produção em 2026, os dois são inseparáveis — Fowler argumenta em _Harness Engineering_ (Thoughtworks, 2026) que harness sem spec é cego (gates validam contra a coisa errada) e spec sem harness é teatro (ninguém enforça). Mas separar para ensinar é correto: misturar os dois logo de cara afoga o iniciante em camadas. O professor está fazendo o que Fowler chama de _capability-gap encoding_ — cada componente do harness existe porque o modelo não consegue algo sozinho; antes de saber qual é a lacuna (o que SDD revela), você não sabe qual harness precisa.

A segunda escolha importante é **não adotar um framework canônico** (Spec Kit, Kiro, Tessl) e gerar skills próprias. Isso tem prós e contras. Pró: você entende o racional, não decora um CLI. Contra: você fica sem vocabulário compartilhado com o resto da indústria. Recomendação para o seu MBA — siga as skills do professor, mas **estude o GitHub Spec Kit em paralelo** (link na bibliografia) porque é o vocabulário que aparecerá em entrevistas, RFCs corporativas e papers a partir de 2026.

A terceira sinalização — "vou pular partes para não ficar maçante" — é honesta e produtiva. Gerar spec com IA é uma conversa lenta de meia-hora a uma hora; vê-la em tempo real é didático nos primeiros 5 minutos e tortura nos próximos 55. O que você precisa internalizar é a **estrutura** do artefato (o que entra em uma spec), não a coreografia da geração.

Por fim, a promessa de "trazer dores reais dos desenvolvedores" é onde o curso ganha valor de mercado. As dores recorrentes em SDD em 2026 são: **prosa ambígua** (resolvido por contratos-em-código), **constitution inflada** (resolvido por limite duro de 5–10 princípios), **tier mismatch** (rodar SDD completo em fix trivial, ou nenhum SDD em feature complexa), e **drift agent-vs-spec** (agente "interpreta" a spec e desvia). Fique atento a esses tópicos nas próximas aulas — eles devem aparecer.

### Deep Dive: Conceitos & Teoria

**Spec-Driven Development (SDD)**

- 🎓 _Na aula:_ Apresentado como metodologia onde "através de especificações e documentações, geramos um sistema". Não há definição formal ainda.
- 🔍 _Deep Dive:_ SDD é a metodologia que emergiu como mainstream em 2025–2026 onde **a spec é o artefato primário e o código é expressão regenerável da spec**. A frase canônica vem do GitHub Spec Kit: _"Specifications don't serve code — code serves specifications."_ A inversão é real: na cultura tradicional, spec era documentação _sobre_ código; em SDD, código é uma **renderização** da spec. Se a spec muda, o código regenera. Debugar muitas vezes é "corrigir a spec", não "corrigir o código". Birgitta Böckeler (Thoughtworks) propõe três níveis de adoção em [_Understanding Spec-Driven-Development_](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html) (15/10/2025): **spec-first** (escreve spec antes, depois descarta), **spec-anchored** (mantém spec viva junto ao código) e **spec-as-source** (spec é o source-of-truth, código tem `// GENERATED FROM SPEC - DO NOT EDIT`).

**Harness e Boundaries**

- 🎓 _Na aula:_ Mencionado como "boundaries", "restrições" ou "harness" — algo que ficará para depois, propositalmente fora desta aula.
- 🔍 _Deep Dive:_ O termo **harness** foi canonizado pela Anthropic em [_Effective context engineering for AI agents_](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) (29/09/2025) e ganhou definição operacional dedicada com Brian Young em _Effective harnesses for long-running agents_ (Nov/2025). É a infraestrutura que executa context engineering automaticamente para coding agents em produção: hooks (pre/post-tool-use), skills com directive descriptions, sub-agents com context isolation, gates classificados (preflight/revision/escalation/abort) e telemetria estruturada. **A ligação com SDD é o ponto cego que o professor adiou:** Fowler, em _Harness Engineering_ (Thoughtworks, 2026), abre com _"correctness is outside any sensor's remit if the human didn't clearly specify what they wanted in the first place"_. Tradução: o harness valida que o agente seguiu instruções, não que as instruções descreviam o que você queria. SDD é a única saída para esse limite.

**A "zona cinzenta" SDD ↔ Harness**

- 🎓 _Na aula:_ O professor identifica a zona cinzenta sem explorá-la, e escolhe começar pelo lado SDD.
- 🔍 _Deep Dive:_ Em meta-harnesses maduros de 2026, a fronteira é codificada via **tier declaration** (padrão _Decision Framework_): `SIMPLE` (1–2 arquivos, fix direto, sem spec), `MEDIUM` (3–10 arquivos, spec leve com contratos de código), `COMPLEX` (10+ arquivos ou requisitos incertos, SDD completo). Um _workflow-gate_ — exemplo de hook — pode bloquear edição de código de produção em `MEDIUM`/`COMPLEX` se não existir um `.md` de spec no diretório. É exatamente aí que SDD encontra harness: a spec vira pré-condição mecânica, não sugestão.

**Skills (recapitulação relevante para SDD)**

- 🎓 _Na aula:_ O professor menciona que criou skills próprias para gerar specs.
- 🔍 _Deep Dive:_ Skills são módulos de expertise com **descrição curta sempre-visível** e **conteúdo denso on-demand** (padrão _progressive disclosure_). O segredo de ativação está na _directive description_: descrições passivas ("this skill helps with X") ativam ~40–60% das vezes; descrições diretivas ("ALWAYS invoke when [triggers explícitos]. Do not X directly.") chegam perto de 100%. Quando o professor mostrar as skills dele, observe a primeira linha de cada uma — esse é o ponto de maior alavancagem.

### Engenharia: Arquiteturas e Padrões

**GitHub Spec Kit** — o framework canônico de SDD em 2026

O GitHub publicou em setembro de 2025 ([anúncio oficial](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)) o **Spec Kit**, um CLI chamado `specify` que materializa SDD com sete _slash commands_:

```
/speckit.constitution  → princípios invioláveis (raramente muda)
        ↓
/speckit.specify       → o QUE construir (user stories, acceptance criteria)
        ↓
/speckit.clarify       → opcional — loop de desambiguação
        ↓
/speckit.plan          → COMO construir (arquitetura, decisões de design)
        ↓
/speckit.analyze       → opcional — revisão sênior
        ↓
/speckit.tasks         → decomposição em tarefas atômicas executáveis
        ↓
/speckit.implement     → execução; gates validam contra critério de done
```

Instalação rápida (suporta Claude Code, Copilot, Gemini, Cursor):

```bash
uvx --from git+https://github.com/github/spec-kit.git specify init meu-projeto
```

- _Funcionamento:_ Instala um diretório `.specify/` no repo com `templates/`, `presets/`, `extensions/`. Cada slash command consome o template correspondente e produz um artefato versionado em markdown. Detecta a feature ativa pelo branch git (ex.: `001-feature-name`).
- _No dia a dia de um SWE:_ Em equipes maduras, o fluxo é: branch novo → `specify` → revisar spec gerada → `plan` → revisar plano → `tasks` → agente executa task por task com gates. Em times pequenos, pula-se `clarify` e `analyze`.
- _Referência externa:_ [github/spec-kit](https://github.com/github/spec-kit) · [Microsoft Dev Blog walkthrough](https://developer.microsoft.com/blog/spec-driven-development-spec-kit) · [DeepWiki Slash Commands Reference](https://deepwiki.com/github/spec-kit/4-spec-driven-development-workflow)

**Contratos-em-código vs. prosa**

Decisão de design dentro do SDD que separa specs amadoras de profissionais. Compare:

```
# Prosa (tradicional, ambíguo)
"O cálculo de frete deve considerar peso, dimensões e região de destino.
 Para entregas dentro da região metropolitana, aplicar tarifa base..."
```

```typescript
// Contrato (forma preferida em 2026)
interface FreightCalculator {
  input: { weight_kg: float, dims_cm: [w,h,d], region: RegionCode, express: bool }
  output: { cost_cents: int, estimated_days: int }
  invariants:
    - cost_cents > 0
    - estimated_days >= 1
    - region=METRO_REGIONAL uses base_tariff
    - express=true applies 1.5× surcharge
}
```

O contrato resolve unidades (kg vs lb), nomes de campos, tipos e invariantes — exatamente onde a prosa quebra quando o agente "interpreta". A prosa sobrevive como complemento (contexto de negócio), nunca como fonte da verdade.

### Pontos de Atenção e Trade-offs

- **A separação SDD vs Harness é didática, não operacional.** Em produção, eles são duas faces da mesma moeda — Fowler chama harness de "o que enforça spec". Esteja consciente de que o professor está fatiando para ensinar; depois você vai ter que costurar.
- **Skills próprias vs framework canônico:** ganho em entendimento, perda em interoperabilidade. Para o portfólio do MBA, vale ter ambos — saiba defender por que escolheu não adotar Spec Kit _e_ saiba operar Spec Kit se a empresa pedir.
- **SDD não paga em todos os contextos.** Heurística operacional: solo + protótipo = overkill (use só craft); time pequeno + feature de 1 semana = SDD leve (plan + tasks); time médio em produção = spec por feature; time grande ou domínio regulado = SDD completo com constitution; _agent-heavy delivery_ (vários agentes gerando código) = **obrigatório**, sem spec há colisão de decisões.
- **Constitution inflada é morte silenciosa.** Times escrevem 50 princípios e ninguém lembra. Limite duro: **5–10 princípios invioláveis**. Mais que isso vira sugestão esquecida.
- **Tedium da geração é real.** A advertência do professor sobre "meia hora gerando docs" não é exagero — equipe da Marmelab gerou 8 arquivos e 1.300+ linhas de spec para uma feature simples de exibição de data. Tier matching (SIMPLE/MEDIUM/COMPLEX) existe justamente para evitar overengineering.
- **Ambiguidade da prosa só aparece 6 meses depois.** Quando ninguém lembra o que "considera peso e dimensões" queria dizer, e o agente começa a regenerar código com decisões diferentes a cada sessão. Contratos previnem.

### Nota do Pesquisador

> **Observação:** O professor descreve SDD e harness como universos a serem trabalhados separadamente, e isso é correto **como estratégia pedagógica**. Vale o aluno saber, no entanto, que a literatura de referência de 2026 (Fowler, Anthropic, GitHub) trata os dois como inseparáveis em produção. A própria _limit-statement_ de Fowler — _"correctness is outside any sensor's remit if the human didn't clearly specify what they wanted"_ ([Harness Engineering, Thoughtworks 2026](https://martinfowler.com/articles/exploring-gen-ai.html)) — é o argumento exato pelo qual harness sem SDD é cego. Quando o professor reabrir o tema "boundaries" mais à frente, é provável que essa costura apareça. Se não aparecer, é uma lacuna que vale levantar em discussão.

### Quiz Prático

**Perguntas sobre a aula:**

1. Por que o professor optou por separar SDD de harness/boundaries logo no início do capítulo, mesmo sabendo que na prática os dois andam juntos?
2. O professor disse que criou skills próprias em vez de adotar um framework. Que trade-off essa escolha implica para um aluno que vai aplicar SDD em uma empresa depois do curso?
3. Você está numa empresa que decidiu adotar SDD e seu time tem 4 pessoas trabalhando numa feature de ~1 semana. Faz sentido implementar o ciclo completo de 7 passos do Spec Kit (constitution → specify → clarify → plan → analyze → tasks → implement)? Justifique.

**🚀 Desafio (conteúdo extra pesquisado):**

4. Birgitta Böckeler descreve três níveis de SDD: spec-first, spec-anchored e spec-as-source. Em qual nível um marcador como `// GENERATED FROM SPEC - DO NOT EDIT` no topo do código fonte faz sentido, e por quê esse nível ainda é raro em 2026?

---

**Respostas:**

1. **Para isolar capability-gaps.** SDD revela O QUE o modelo precisa especificado para executar bem; harness é a infraestrutura que enforça isso e cobre lacunas adicionais. Misturar os dois antes de entender SDD puro faz o aluno confundir "regra que veio da spec" com "regra que veio do hook" e impede _capability-gap encoding_ consciente (frame de Rajasekaran/Anthropic, mar/2026).
    
2. **Trade-off: profundidade conceitual vs vocabulário compartilhado.** Skills próprias forçam o aluno a entender o racional de cada artefato (constitution, specify, plan, tasks), o que é ouro para tomada de decisão. Mas em 2026 o vocabulário do GitHub Spec Kit virou _de facto_ — RFCs, entrevistas e papers usam termos como `/speckit.constitution`, `spec-anchored`, `tier declaration`. A defesa é estudar Spec Kit em paralelo como segundo idioma.
    
3. **Não, não faz sentido.** Para 4 pessoas + 1 semana, o ciclo completo é overkill — vira burocracia teatral, frustra o time e o método é abandonado. A heurística operacional de 2026 indica **SDD médio** nesse contexto: pular `constitution` (a menos que haja conflito recorrente), pular `clarify` e `analyze` (úteis em times de 20+), e rodar essencialmente `specify → plan → tasks → implement`. Mesmo assim, prefira contratos-em-código a prosa.
    
4. **Faz sentido em spec-as-source**, o nível mais radical, onde a spec é o artefato mantido e o código é regenerado a partir dela. É raro em 2026 porque exige confiança altíssima na qualidade da geração — só funciona em domínios maduros como geração de stubs de API a partir de OpenAPI ou código embarcado certificado a partir de modelos Simulink. A Tessl tenta estender isso a software geral, mas ainda em beta. A maioria dos times adota _spec-first_ (descarta a spec após gerar) ou _spec-anchored_ (mantém spec viva junto ao código).

**Ferramentas relacionadas:**
